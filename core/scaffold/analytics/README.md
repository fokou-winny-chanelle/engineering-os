# analytics (dbt + DuckDB)

Generated by `eos scaffold analytics`; yours to edit. A small, working ELT project: synthetic seeds stand in for
raw loads, staging models rename and cast, marts hold business logic at a stated grain.

Run locally (no server needed):

    cd analytics
    uv run --no-project --with dbt-core --with dbt-duckdb dbt build --profiles-dir .

What `dbt build` checks here:

- generic data tests (`unique`, `not_null`, `accepted_values`, `relationships`) in `_staging.yml` and `_marts.yml`
- a unit test of the daily aggregation logic (fixed input rows, expected output)
- an enforced model contract on `fct_daily_payments` (column names and types checked before building)
- a singular reconciliation test: money in the mart equals money in staging (`tests/`)

The published shape of `fct_daily_payments` is also described in `contracts/payments-daily.odcs.yaml` (Open Data
Contract Standard). Change a column there and in the model together; `eos data check --base origin/main` fails a
breaking change unless the major version goes up.

Moving to a warehouse: add a target in `profiles.yml` that reads credentials with `env_var()`; keep the `ci` target
on DuckDB so pull requests stay fast and need no secrets. Note that dbt's newer engine (v2) does not list Postgres
as a supported adapter at the time of writing, which is why this scaffold pins dbt-core v1 (see
.eos/packs/ref/analytics/dbt-elt.md).

Money is integer XAF. Amounts are never floats. Timestamps are UTC.
