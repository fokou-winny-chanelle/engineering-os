## 1. Framing

- [ ] The decision this model supports is written down, with who acts on it and what happens on a wrong answer.
- [ ] A non-ML baseline exists (rule, heuristic or simple model) and its score on the same test set is recorded.
- [ ] The metric matches the cost of errors (for rare positives such as fraud: precision/recall or PR-AUC at the
      operating threshold, not accuracy).

## 2. The split

- [ ] The split was made **before** any fitting, scaling, imputation, encoding or feature selection.
- [ ] Every preprocessing step lives inside a `Pipeline` fitted on training data only (never `fit` on test data).
- [ ] Rows from one entity (customer, card, device, merchant, patient) are in one split only (`GroupKFold`).
- [ ] Data with a time order is split by time; the test period comes after the training period.
- [ ] The gap between train and test is at least the label delay (for example chargebacks that arrive weeks later).
- [ ] Duplicates and near-duplicates were removed before splitting.
- [ ] The test set was not used to choose features, hyperparameters or thresholds (use a validation split).

Automated check (exports each split to CSV first):

    python3 .eos/bin/eos.py data split --train train.csv --val val.csv --test test.csv \
        --id customer_id --time event_at --gap-days 30 --target label

It reports shared ids (SPL001), identical rows (SPL002), time overlap or a short gap (SPL003), a column that alone
determines the label (SPL004, warning) and outcome-like column names (SPL005, warning).

## 3. Features available at prediction time

For each feature, answer: would this value exist, with this content, at the moment we predict?

| Feature | Source | Known at prediction time? | Computed as of (point in time) |
|---|---|---|---|
| | | | |

- [ ] No feature is computed from data after the prediction time (refund flags, chargeback dates, "closed_at").
- [ ] Aggregates (counts, averages) use only events before the prediction time.
- [ ] Training features and serving features come from the same code or the same feature definitions.

## 4. Sanity checks on results

- [ ] A score that looks too good was investigated (a near-perfect score usually means leakage).
- [ ] Feature importances were read; a surprising top feature was explained.
- [ ] Results hold on a later time slice, not only the random test split.
- [ ] Performance is reported per important segment (region, channel, new vs returning), not only overall.
