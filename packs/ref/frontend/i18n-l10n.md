# i18n and localisation (French/English, XAF, Africa/Douala)

Build bilingual from the first screen: retrofitting string extraction, plural rules and locale-aware formatting later costs far more than starting with them.

## Decision guide

**1. Library and routing.**
- Next.js App Router: next-intl (Server and Client Components, request-scoped config via `getRequestConfig`, ICU messages, `useFormatter`/`getFormatter`, proxy-based locale negotiation, typed keys). The Next.js guide's minimal approach (JSON dictionaries loaded in a `server-only` module, `@formatjs/intl-localematcher` + `Accept-Language` in `proxy.ts`) is fine for small sites.
- React Native / Expo: i18next or the same ICU messages with `expo-localization`; share the JSON catalogs in a package.
- Routes: prefix (`/fr/...`, `/en/...`) for public, indexable pages (each URL has one language; add `hreflang` alternates); cookie/user setting for logged-in apps. Negotiate from `Accept-Language` once, then remember the explicit choice; always show a visible switcher labelled in the target language ("English" / "Français").
- Set `<html lang>` to the active locale (screen readers and hyphenation depend on it).

**2. Messages.**
- Keys by feature (`checkout.pay`), never English sentences as keys. One JSON per locale (`messages/fr.json`, `messages/en.json`), same key set.
- Whole sentences with ICU arguments, not concatenated fragments: `"{count, plural, one {# article} other {# articles}}"`. Word order differs between languages.
- French plural categories (CLDR): `one` covers 0 and 1 (and decimals below 2, e.g. 1.5); `many` exists for exact millions ("1 000 000 de jours"); `other` for the rest. English: 0 is `other`. Every plural/select needs an `other` branch; use `=0` for a special zero message.
- Gender/formal address: French UI usually uses "vous"; agree on a glossary early so translators stay consistent.

**3. Numbers, money, dates.** Use `Intl` (or next-intl's formatter, which wraps it); never hand-format.
| What | Code | Output (Node 20, ICU 76 / CLDR 46) |
|---|---|---|
| XAF in French | `new Intl.NumberFormat('fr-CM', { style: 'currency', currency: 'XAF' }).format(1234567)` | `1 234 567 FCFA` (narrow no-break spaces U+202F between groups, no-break space U+00A0 before FCFA) |
| XAF in English | same with `'en-CM'` | `FCFA 1,234,567` (U+00A0 after FCFA) |
| date + time | `new Intl.DateTimeFormat('fr-CM', { dateStyle: 'long', timeStyle: 'short', timeZone: 'Africa/Douala' })` | `10 octobre 2026 à 19:00` / en-CM `10 October 2026 at 19:00` |
- XAF has no minor unit (ISO 4217 exponent 0): store integer francs, and `Intl` rounds fractions away, so never pass computed floats (`data/keys-money-time`).
- Always pass `timeZone` (store UTC, display `Africa/Douala`, UTC+1 without daylight saving) so server-rendered and client-rendered output match; next-intl otherwise uses the server runtime's time zone, so set `timeZone` (and `now` for relative times) in `i18n/request.ts`, which also keeps server and client output identical.
- Parsing user input: strip spaces (including U+202F/U+00A0) and thousands separators before validation (`frontend/state-forms`); accept both `,` and `.` only where unambiguous.
- Tests must compare against these exact characters; a test expecting a normal space fails.

**4. Layout.** French strings are often longer than English; the W3C notes short strings can grow two to three times in translation. Avoid fixed-width buttons and truncation of labels, test the longest locale, and let text wrap. Don't put text in images.

**5. Completeness in CI.** `eos i18n check` (also part of `eos check` when catalogs exist) compares every locale with the default: missing and extra keys, empty values, a string in one locale where another has a nested object, ICU argument names that differ (`{name}` vs `{nom}`), plural/select without `other`, and keys used in code (`useTranslations('ns')` / `getTranslations` + `t('key')`) that do not exist. Configure `frontend.i18n` in `.eos/config.json` (`dir`, `default_locale`) when auto-detection misses your layout.

## Examples
```ts
// lib/format.ts (from `eos scaffold i18n`)
export const TIME_ZONE = "Africa/Douala";
export const formatXaf = (francs: number, locale: "fr" | "en") =>
  new Intl.NumberFormat(locale === "fr" ? "fr-CM" : "en-CM", { style: "currency", currency: "XAF" }).format(francs);
export const formatDateTime = (d: Date, locale: "fr" | "en") =>
  new Intl.DateTimeFormat(locale === "fr" ? "fr-CM" : "en-CM", { dateStyle: "long", timeStyle: "short", timeZone: TIME_ZONE }).format(d);
```
```json
{ "orders": { "count": "{count, plural, =0 {Aucune commande} one {# commande} other {# commandes}}" } }
```

## Anti-patterns
- `amount.toLocaleString() + " FCFA"`, hard-coded `"XAF"` prefixes, or `toFixed(2)` on francs.
- Formatting dates without `timeZone` (server in UTC, browser in WAT: hydration mismatch and wrong day near midnight).
- `t('you_have') + count + t('items')`; English fallback text shipped silently for missing French keys.
- Locale only in client state, so server-rendered pages and emails come out in the wrong language.
- Validation and error messages left in English because they come from the schema library.

## Checks
- `eos i18n check` in `eos check`/CI; `eos scaffold i18n` adds catalogs, `lib/format.ts` (with a strict amount parser that rejects decimals) and Vitest tests pinning the U+202F/U+00A0 output.
- e2e: run key flows in both locales; screenshot review of the French layout (`testing/e2e-playwright`).
- Review: new text goes through `t()`; money via `formatXaf`; dates pass `timeZone`.
