# Mobile area: source survey (verified 10 October 2026)

Stage 9 of the knowledge library (docs/LIBRARY.md checklist, step 1). Every source below was opened on 10 October 2026 (box clock, WAT) and the facts the refs rely on were checked against the page text (fetched and grepped, not recalled). Every link in the refs returned HTTP 200 on that date; GitHub "blob" pages returned 503 to both fetchers, so those were replaced with `raw.githubusercontent.com` links to the same files. Versions were read from the vendors' own pages and registries the same day: Expo SDK 57 (React Native 0.86, React 19.2; Android 7+, iOS 16.4+) with SDK 58 in beta; React Native 0.87 stable (0.88 RC); Flutter 3.47.7 / Dart 3.13; Maestro CLI 2.11.0 (release checksum recorded in versions.toml); Detox (officially tested on React Native 0.77–0.84); Patrol 4.x. Verdicts follow the import policy in `v0.7-external-sources.md`.

**Imports: none. Adaptations: none.** All twelve `mobile/*` refs and the updated `testing/mobile-qa` are our own text that cites the sources. Reasons nothing was vendored: vendor documentation (Apple, Google, Expo, Flutter, Firebase) is either all-rights-reserved or CC BY with fast-moving content where a pinned copy would go stale within one SDK cycle; OWASP MASVS/MASTG are CC BY-SA 4.0 (share-alike is not on our copy allow-list) and the OWASP sign-off pending since stage 2 stays pending. Expo docs and the Maestro (GitBook) docs embed "instructions for AI agents" blocks; these were treated as page data and ignored, and they are one more reason not to vendor those pages (injection risk). Nothing new waits for `eos vendor review`.

## 2. Claims deliberately not made
- Android docs' wording on pinning: we quote OWASP's cheat sheet ("almost no situation") and Android's warnings about backup pins and expiry; we do not claim Android "does not recommend" pinning, because the page text we fetched did not say so in those words.
- A fixed "5-second cold start" threshold: the launch-time page describes TTID/TTFD and excessive-start reporting, but we did not find a single current threshold on it, so the budget doc asks teams to set their own number on a reference device.
- Third-party claims about typical APK sizes (blog posts) were not used; size advice cites Android, Flutter and Expo docs only.
- The Orange developer portal returned 403 to both fetchers, so nothing is claimed about the Orange Money API beyond "server-side confirmation, never trust the client"; MTN's FAQ is cited for callbacks.
- `isLowRamDevice` behaviour and "SDK supported for about a year" statements were dropped: no page we fetched said so.
- SafetyNet Attestation: only that it was turned down on 31 January 2025 and Play Integrity replaces it.
- No prices for EAS, device farms, Codemagic or Bitrise: plans change and were not needed for any decision.

## 3. Enforcement decisions
- **`eos mobile check`** (in-process, no tools): MOB001 backup on, MOB002 cleartext (manifest, network security config, Expo build properties), MOB003 debuggable, MOB004 exported service/receiver/provider without a permission, MOB005 intent-filter without `android:exported`, MOB006 ATS arbitrary loads, MOB007 secret-looking names behind public env prefixes (`EXPO_PUBLIC_*`; MASVS-CRYPTO-2/STORAGE), MOB008 expo-updates without runtimeVersion (warning), MOB009 deep link without verification (warning), MOB000 unparsable config (warning). Debug source sets and local emulator hosts are skipped; only git-tracked `.env*` files are read. Exceptions go in `.eos/config.json` → `mobile.allow` with a written reason, so they are visible in review.
- **`eos mobile size`**: size ratchet on .aab/.apk/.ipa (max 5% and at least 100 KB growth by default) plus optional absolute budgets; prints a breakdown by ABI, dex and assets and says that an AAB is not the download size (Play generates per-device APKs).
- **Lanes**: trivial/spike nothing; standard runs the config check only if mobile config files changed; risky/one-way-door/`--full` also run the size ratchet when a built package newer than the change exists. The fast path is unchanged. `src/main/AndroidManifest.xml` and `res/xml/network_security_config.xml` are now risky paths (exported components and cleartext are security decisions).
- **`eos scaffold mobile`**: 14 Semgrep rules (RN/TS, Dart, Kotlin, Swift) with ruleid/ok fixtures; Maestro smoke and offline-sync flows; an emulator E2E workflow (nightly, manual or `e2e` label, never on every PR because emulator runs are slow) with all actions SHA-pinned and the Maestro download checked against the release SHA-256; a low-end performance budget document.
- **Not enforced, on purpose**: root/jailbreak detection and obfuscation (MASVS-RESILIENCE is a profile choice, not a baseline); certificate pinning (usually harmful); store-policy compliance (needs a human reading the current guidelines).
