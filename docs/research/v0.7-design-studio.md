# Design studio: importing impeccable and ui-ux-pro-max safely (v0.7, 2026-10-10)

The user approved integrating two design-skill repos that stage 8 had rejected
(`pbakaus/impeccable`, `nextlevelbuilder/ui-ux-pro-max-skill`) under a plan:
pin and review, separate knowledge from code, load on demand, one design authority, prove it with an A/B test.
This file records what was reviewed, what was imported and why, and how the A/B test decides whether they stay.
All checks below were run on 2026-10-10 (times WAT).

## 2. Code review: what the code does

### impeccable

- **What runs.** `skill/scripts/impeccable` (POSIX sh launcher, 8.5 KB) execs a Rust engine binary. Its order: `$IMPECCABLE_BIN`, a sibling binary, `~/.impeccable/bin/impeccable`, a version-pinned cache, `impeccable` on PATH, and **as a last resort downloads** `engine-v<VERSION>/impeccable-<os>-<arch>` from GitHub Releases, verifying it against a `.sha256` sidecar fetched from the same release (fails closed when the sidecar or a hash tool is missing).
- **Binary provenance.** Release `engine-v0.1.14` (published 2026-10-09 02:54 UTC = 03:54 WAT) is built by `.github/workflows/release-engine.yml` from the tag (actions pinned by SHA, `cargo build --release`, sha256 sidecars written in the publish job, no `--clobber`). The Windows build is Authenticode-signed; **Linux and macOS builds have no signature and no GitHub artifact attestation** (attestations API: 404). The only upstream integrity data is the sha256 sidecar plus GitHub's own asset digest, which agree:

  | Asset | sha256 (sidecar = GitHub asset digest) |
  |---|---|
  | impeccable-linux-x64 | `3d31ec1a664ac35c815ea1d7c10abad1155ce364d0f461157eb837a34368efb6` |
  | impeccable-linux-arm64 | `396263ee694780db942483fc80933a012ef08bf981f5f26b0da5e16b6208c948` |
  | impeccable-darwin-arm64 | `abbd69d540532b91e9599c41d3a6127dfbaabae5e24bafd74ff7e2fb18f4f87c` |
  | impeccable-darwin-x64 | `dfa4570309939f49615a441baa9c73f1c2d339bf07494517a6c6eb2eb28aa0f5` |

  The linux-x64 asset downloaded here hashes to the same value; it is a statically linked musl binary.
  **Decision:** an upstream-published checksum exists, so the binary is allowed, but only (a) downloaded by
  `eos studio fetch impeccable`, (b) verified against **our pinned hash** (above, in `core/studio/studio.json`)
  *and* the live sidecar, (c) never committed, never put on PATH, and (d) executed only inside the studio
  sandbox with no network. A same-origin checksum proves the bytes match what the release published, not who
  built them; pinning the hash in our repo means a later swap upstream is caught (trust on first use, reviewed today).
- **Network (from the Rust source, `crates/`).** `ureq` HTTPS client used for: `update`/`install` (GitHub
  releases), an update check and a findings "staleness" check, the concept-seed "roll" API
  `https://impeccable.style/api/roll` (design-direction cards), a telemetry ping `pingChosen` after a direction is
  chosen (off with `IMPECCABLE_NO_TELEMETRY` or `DO_NOT_TRACK`), and image generation through
  `https://api.openai.com/v1` (needs a user key). A local HTTP "live" server on localhost and a Chrome DevTools
  driver for URL scans and live editing.
- **File writes.** `~/.impeccable/` (binary cache, update cache), `.impeccable/` in the project (config,
  critiques, ignores), `DESIGN.md`/`PRODUCT.md` when asked, and `hooks`/`install`/`link` write agent harness
  configuration (skills folders and edit hooks for many agents).
- **Telemetry.** Yes, the opt-out ping above; no other analytics libraries found.
- **What is useful offline.** `detect`: a static anti-pattern scanner with 58 rules (e.g. `ai-color-palette`,
  `overused-font`, `gradient-text`, `nested-cards`, `low-contrast`, `tiny-text`, `line-length`, `em-dash-overuse`,
  `marketing-buzzword`, `hero-eyebrow-chip`, `numbered-section-labels`, `bounce-easing`). Verified to run under
  `bwrap --unshare-all` (no network), with a read-only project and an empty scratch HOME, writing nothing.
- **Instruction text.** The router `SKILL.md` tells the agent to run the launcher (which may download) and opens
  with a persona line ("Go all out. No hedging…"). **Not vendored**; our studio guide replaces it. The 39
  reference playbooks are vendored (one scan hit: an HTML comment template in `document.md`, held for a human).

### ui-ux-pro-max

- **What runs.** Five Python files (`search.py`, `core.py`, `design_system.py`, `reasoning_contract.py`,
  `validate_data.py`): standard library only (csv, re, json, difflib, math, tempfile); **no network, no
  subprocess, no telemetry**. BM25 search over the CSV catalogs; `--design-system` composes a palette, type
  pair, style and checklist. Writes only with `--persist` (to `<output-dir>/design-system/<slug>/MASTER.md`,
  atomic temp-file replace).
- **Not imported:** the npm CLI `uipro-cli` (`cli/`): it calls the GitHub API, downloads release zips and
  extracts them with `child_process`. Also the `gallery/`, `preview/`, `stack/` demo apps.
- **Knowledge:** `SKILL.md` (~4.0k tokens), `references/quick-reference.md` (~6.1k) and `pro-rules.md` (~2.7k),
  `data/` (17 CSV/JSON catalogs, ~650k tokens if read whole, plus 22 stack CSVs ~121k): never loaded whole;
  queried through the sandboxed search script or eos's own read-only `eos studio find`.
- One note for honesty: during review the search script was run once directly on this box (after reading it:
  stdlib only, no network) to see its JSON output; every later run used the sandbox.

## 4. Sandbox design (`eos studio`)

- **Opt-in, per project.** `eos studio on` copies the signed-off sources into `.eos/studio/` (knowledge in
  `vendor/`, code in `code/`, our `README.md` as the entry point, `out/` git-ignored). It **refuses while any
  source is pending human sign-off**. `eos studio off` deletes the folder. Nothing is added to `AGENTS.md`,
  rules, skills or hooks, and dot-folders are renamed (`.claude` → `dot-claude`) so no agent harness discovers
  the vendored skills by itself. `eos verify`, hooks and the fast path do not know the studio exists.
- **Code runs only in a sandbox**, chosen automatically (override with `EOS_STUDIO_SANDBOX`):
  - Docker or Podman: `--network none --read-only --cap-drop ALL --security-opt no-new-privileges
    --pids-limit 256 --memory 1g`, a `/tmp` tmpfs, your uid, an image pinned by digest
    (`python:3.14-slim@sha256:a2b82f3c…`), the project mounted **read-only**, only `.eos/studio/out/` writable,
    and an environment holding only `HOME=/out`, `PATH` and the tool's own off-switches (no secrets).
  - bubblewrap (Linux, no daemon): `--unshare-all` (no network), `--clearenv`, `--die-with-parent`, system
    folders and the project read-only, `out/` writable. Tested on the box: a socket connect inside fails with
    "Network is unreachable", the environment holds 4 variables, `/etc` is not writable.
  - **None available → knowledge-only mode**: `eos studio run` exits 3 with a message; `eos studio find`
    (eos's own read-only search over the text and CSV catalogs) and reading the files still work.
- **Allow-lists.** impeccable: verbs `detect`, `help`, `--help`, `--version` only; no URLs (they need a browser
  and network); flags limited to `--json --quiet --scope --no-config --no-advisory --no-design-system
  --no-inline-ignores --help`; paths must stay inside the project. Its telemetry, update and staleness checks are
  switched off by environment variable as well as by the missing network. ui-ux-pro-max: verb `search`;
  `--output-dir` is refused and `--persist` writes only to `out/`.
- **impeccable binary.** `eos studio fetch` downloads `impeccable-<platform>` for engine v0.1.14 from the GitHub
  release, and keeps it only if its sha256 equals **both** the hash pinned in `core/studio/studio.json` **and** the
  upstream `.sha256` sidecar. It lives in `~/.cache/engineering-os/studio/` (`EOS_STUDIO_CACHE`), mode 0555,
  never on `PATH`, never committed, and is re-hashed before every run. Limit, stated plainly: the sidecars come
  from the same release as the binary and macOS/Linux builds are not signed, so the pin protects against a
  changed file after our review, not against a compromised upstream build.
- **How to run** (after a human signs off the sources):

  ```sh
  eos studio on                                   # in the project
  eos studio fetch                                # optional: the impeccable engine (verified)
  eos studio find "form error message"            # works without any sandbox
  eos studio palette "fintech mobile money" -p Kolo
  eos studio run uupm search "payment form" --domain ux
  eos studio run impeccable detect src
  eos studio status | off
  ```

## 6. A/B evaluation

**Harness** (no agent or model runs on the box, so the live comparison is for the maintainer to run):
`eos design ab init <ws> --allow-pending` creates `arm-a/` (our packs and refs) and `arm-b/` (the same plus the
studio), the same three specs (`core/templates/design/ab/`: SME cash dashboard, ENEO bill payment by mobile
money, njangi savings-group landing page) and the same `PROMPT.md` apart from its Context section.
`--allow-pending` is the only way unsigned sources leave quarantine, and the arm is stamped
`PENDING-SIGN-OFF.txt`. After one fresh agent session per arm: `eos design ab score <ws> [--shoot]` runs
`eos design check` on every screen, copies screens to `scoring/<screen>/X|Y` (random per screen; key in
`.ab-key.json`), warns if a screen names the studio (blinding leak), writes blank 12-row critique sheets and a
Playwright screenshot script; a person scores the sheets; `eos design ab report <ws>` unblinds and decides.

**Decision rule.** Keep the studio only if all hold: (1) B's mean critique total ≥ A's + 2 (of 24); (2) B wins
≥ 2 of 3 screens; (3) no new 0 on gate rows 5, 7, 9, 10; (4) B's `eos design check` errors ≤ A's. Otherwise
drop it. Ties and small wins are a drop. impeccable's `detect` counts are recorded but are not in the rule
(arm B read its rules).

**Static evaluation done here** (`tests/bench/studio_static_eval.py`; results in
`tests/bench/results-v0.7.0-dev.json` → `design_studio`):

| Check | Result |
|---|---|
| ui-ux-pro-max palettes with a stock Tailwind v3 hex as primary/secondary/accent | 189 of 192 (Tailwind 3.4.17 colours, 241 hexes) |
| … with a violet/indigo key colour (OKLCH hue 270–330, chroma > 0.08) | 45 of 192 |
| … declared on-colour pairs passing 4.5:1 | 1,344 of 1,344 |
| Font pairings using a family our lint calls a default | 16 of 74 (8 with Inter) |
| Palettes it suggests for our 3 specs, through our review | dashboard: violet accent/CTA `#8b5cf6` + Inter body; payment: Inter heading; landing: no warning. No contrast errors |
| Rubric "mentions it" proxy (paragraphs/rows matching row keywords; ours 173 units vs ~6,100) | the studio mentions every row more often in raw count, except row 11 (low-end phone, data cost, literacy): ours 21, impeccable 10, ui-ux-pro-max 17 |

What this says: the studio adds breadth (catalogs, task playbooks, a 58-rule detector), not judgement about
our context, and its default palettes and fonts point toward exactly the generic looks our refs reject. That is
why its output must pass through tokens and `eos design check`. Static checks cannot show whether screens get
better; only the A/B run can. **Status: undecided until the A/B is run; default is drop.**

**Lint gap found and fixed.** Comparing with impeccable's rules showed our lint missed purple/indigo gradients
written as raw CSS (`linear-gradient(90deg, #8b5cf6, #6366f1)`); it only caught Tailwind classes. `eos design
check` now flags literal violet stops in CSS gradients (same hue band). Rules impeccable has that our lint only
names in the pack (not automated): `hero-eyebrow-chip`/`kicker-above-heading`, `numbered-section-labels`,
`cream-palette`, `nested-cards`, `gradient-text`, `em-dash-overuse`, `line-length`, `tiny-text`. Candidates
for our own lint later; not added now.

**Conflicts to remember.** impeccable's overused-font list includes Fraunces and Space Grotesk (our lint lists
Space Grotesk too; Fraunces is fine for us if chosen on purpose). ui-ux-pro-max palettes use Tailwind stock
values. Copy rules in both are English-only. Precedence is written in the design-direction pack and the studio
README.
