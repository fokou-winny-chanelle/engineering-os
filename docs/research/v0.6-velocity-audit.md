# Velocity audit (v0.6.0): where eos slowed you down, and what changed

Question: across engineering-os v0.5.0 and the blueprint, where does the system **slow a solo developer down** instead of making fast, correct progress? Method: walk ten real workflows end to end, count every gate, approval, artifact, hook, CI wait, BMAD step, memory update, eos command and agent instruction, then cut or reshape whatever doesn't pay for itself. Safety for money, auth, secrets and force pushes stays.

How to read the numbers:
- **Measured (M)**: wall-clock on this machine with `tests/bench/bench_hooks.py` (same fixture for both versions, median of 15 runs, v0.5.0 and v0.6.0 run back to back) or token counts with the same script as every release (4 characters per token; real tokenisers vary by about 20%).
- **Counted (C)**: steps read from the rules, hooks and configs each version installs.
- **Estimated (E)**: agent or human time. These are judgements, not measurements, and are labelled as such.
- CI wall time was **not** measured (no live CI run in this audit); only structural changes were made there.

## 1. Measured: hook latency and context

| Measurement (M, median / max of 15) | v0.5.0 | v0.6.0 |
|---|---|---|
| Guard hook per agent tool call (read / edit / shell) | 92 / 93 / 99 ms | 44 / 44 / 48 ms |
| `git commit` of a docs typo | 966 ms | 394 ms |
| `git commit` of a `.py` change | 979 ms | 398 ms |
| Stop check when the agent says "done" (.py change) | 522 ms | 420 ms |
| `eos check` | 107 ms | 113 ms (unchanged; now runs only when agent-context files change) |

Where the commit time went: the individual hooks took about 0.35 s together; the rest was pre-commit's own start-up, run twice because v0.5 also installed a `commit-msg` stage (a remote `conventional-pre-commit` hook) and ran `eos check` on every commit. v0.6 drops the commit-msg stage unless release-please is set up (then it uses a local, no-download hook) and runs `eos check` only when agent-context files change. The guard speed-up comes from a tiny launcher (`.eos/bin/hook.py`) that imports `eos.py` so Python caches its bytecode, and from a loop-guard fingerprint that reads `git status` plus file sizes and times instead of hashing the whole `git diff`.

A 40-tool-call agent task paid about 3.7 s of guard time in v0.5 and about 1.8 s in v0.6 (C × M). Small, but it's on every call.

`eos verify` on a 60-test Python fixture (M, earlier run in this audit): standard lane 0.6–1.0 s (hooks on changed files + related tests) vs 3.8 s for the full check that v0.5 asked for before every "done". On a real project the gap grows with the suite size.

Guard false prompts (M, `tests/bench/guard_corpus.py`): 0 of 58 benign commands prompted and 9 of 9 deny cases were denied in both versions. v0.5 asked on 16 of 17 risky commands (it let `git clean -fdx` through); v0.6 asks on 17 of 17. **The guard was not the friction**, so it was not loosened; it was tightened by one pattern.

Context per request (M, FastAPI + Next.js fixture, default `web-app` profile):

| | v0.5.0 (teaching on by default) | v0.6.0 (teaching off by default) | v0.6.0 with teaching on |
|---|---|---|---|
| Cursor | 2,039 | 1,884 | 1,914 |
| Cline | 2,015 | 1,860 | 1,890 |
| Claude Code | 2,062 | 1,907 | 1,937 |
| Codex | 2,015 | 1,860 | 1,890 |
| Cline MCP tool schemas (default MCP profile) | ~4,450 (`build`: GitHub + Context7) | ~1,250 (`minimal`) | ~1,250 |
| **Cline total per request** | **~6,465** | **~3,110** | ~3,140 |

`api` profile: 1,795–1,842; `full`: 1,976–2,023 (v0.5: 1,950–1,997 and 2,131–2,178). The biggest single saving is Cline's ~3,350 tokens per request from not loading the GitHub and Context7 MCP schemas by default; agents use the `gh` CLI instead and you switch profiles when you actually need a server. Over a 30-request session (an assumption, not a measurement) that is roughly 100k input tokens.

## 2. The ten workflows, before and after

Notation per row: agent actions beyond the change itself / local gates that run / artifacts to write / blocking approvals.

### (a) 10-minute bug fix in an existing Python service
| | v0.5.0 (C) | v0.6.0 (C) |
|---|---|---|
| Agent extra actions | full check before "done" (rule 2); rewrite `memory/active-context.md`; append to `memory/progress.md`; run `eos next --brief` and print a suggestion | `eos verify` (hooks on changed files + related tests) |
| Local gates | guard per call (~90 ms); stop check 0.52 s; commit 0.98 s incl. commit-msg format check (a wrong format rejects the commit); pre-push typecheck + tests | guard (~45 ms); stop check 0.42 s; commit 0.40 s; pre-push typecheck + tests (kept) |
| Artifacts | 2 memory files | none |
| Approvals | none | none |
| Extra time (E) | ~2–5 min: the full suite at "done" and memory edits, plus pre-push | ~10–30 s |

Verdict: the memory edits and the per-task navigator call were pure overhead on a fix that lives in one commit; git history already records it. The full check before "done" duplicated pre-push and CI.

### (b) Typo or copy change
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Agent extra actions | same as (a): full check, 2 memory edits, `next --brief` | none beyond `eos verify` = hooks on the one changed file |
| Local gates | commit 0.97 s (M) incl. `eos check` and commit-msg | commit 0.39 s (M) |
| CI | full eos-core jobs | same jobs (kept); the Lane step labels the PR "trivial" |
| Extra time (E) | ~2–5 min | ~seconds, plus the PR |

Verdict: the worst ratio of ceremony to change in v0.5. Trivial lane now. Still kept: a branch and a PR (no-commit-to-branch on `main`), because "it's only a typo" is how unreviewed changes reach `main`, and the PR is one `gh pr create --fill` away.

### (c) Medium feature (1–2 days, several modules)
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Plan | required and **blocking** ("spans several modules", rule 1) | `eos new plan` for multi-session work (resumability, not a gate); no wait unless the lane is risky with money/auth/security |
| Per task (say 10–15 tasks) | full check + memory edits + `next --brief` each time (C: ~30–45 extra agent actions) | `eos verify` each time (C: 10–15) |
| Session end | rewrite active-context, append progress | `memory/handoff.md` only if unfinished |
| Large diff | no special handling | > 20 files or > 400 lines → risky lane: full check in verify, human review listed |

Verdict: the "several modules" approval wait blocked the most common productive work. Size is now a signal (large diff → risky), not module count.

### (d) Risky money/auth change (e.g. a refund rule in `payments/`)
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Detection | agent judgement from the rule text | `eos lane`: path tokens (`payment`, `auth`, `billing`, `token` as a whole word, …), migrations, infra; CI job summary lists the flagged files |
| Plan | written, blocking | 5 lines incl. rollback, **blocking** (money behaviour) — kept |
| Checks | full check | `eos verify` = full check + strict test-integrity — kept |
| Review | human, money/auth listed in PR | human reviews the flagged files line by line; fresh-session AI review recommended — kept |
| Overhead removed | memory edits, `next --brief` | — |

Verdict: here the ceremony **is** the value. Nothing safety-related was cut.

### (e) Spike / prototype to throw away
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Mode | none: the same rules as production code. Stop check blocked "done" on lint failures; test-integrity blocked skips; plan wait if several modules | `eos spike try-x` → `spike/try-x` branch; rule 8: no tests, plans or docs; stop check off |
| Kept on | — | guard (secret reads, force pushes, protected paths), gitleaks at commit |
| Exit | nothing recorded; code could drift into `main` | `eos spike done` writes `docs/spikes/<date>-<slug>.md` from the git log; CI fails a PR from `spike/*` |
| Extra time (E) | tens of minutes fighting checks on code meant for the bin | ~0 |

Verdict: v0.5 had no escape hatch, which in practice teaches `--no-verify`. A sanctioned fast lane with a hard "never merge" wall is safer than an unofficial one.

### (f) Adopt a messy repo and ship a fix the same day
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Setup | `eos adopt` (ratchet gates, baseline, improvement plan) | same (it was already non-destructive) |
| First commit | hook environments downloaded on first commit (network); commit-msg remote hook | hooks warmed in the background at init while you're online; no commit-msg download |
| Navigator | blocked on every `.eos-new` file and showed generic phase steps | `.eos-new` is a note; `eos next --skip` hides steps you don't need |
| Memory | active-context and progress seeded, then nagged when stale | not seeded |
| Answers | teaching mode on (longer answers) | off |
| The fix | full check before "done" — on legacy code the ratchet keeps it passable, but slow | related tests only; the ratchet still blocks new problems at pre-push |
| Linters | the repo's own ruff could lint and reformat eos's generated files | `.eos/ruff.toml` excludes them ("closest config" wins) |

### (g) Night-time production hotfix
| | v0.5.0 | v0.6.0 |
|---|---|---|
| Start | manual branch; the same full ceremony; plan wait if auth is touched | `eos hotfix login-500`: fetches `origin/main` with a 15 s timeout (`--no-fetch` offline), branches `hotfix/login-500` |
| Rules | full check, memory, conventional commit message | rule 8: smallest fix + a regression test, no refactors; `eos verify` |
| Merge | PR, CI, review | PR labelled `hotfix`, merge on green CI; money/auth files still flagged for a second person |
| After | nothing | `eos hotfix done` writes `docs/incidents/<date>-<slug>.md` with the git timeline; review it within a working day |

### (h) Cross-repo change in a multi-repo workspace
Mostly unchanged on purpose: one PR per repo, linked; contract checks (oasdiff / buf) in each repo; the workspace manifest. Per-repo context is smaller (section 1). The lane classifier flags a contract file with removed lines as **one-way-door** in the repo that owns it, which is exactly where the approval belongs.

### (i) Brainstorming a new product idea
No code means no gates fire in either version; the cost was context and prompting. v0.5: teaching on, the navigator skill listed, a next-step line after every answer, the 12-step greenfield table presented as *the* workflow, and a suggestion to switch MCP profiles and models between steps. v0.6: the discovery/ideation packs still load on demand; no per-answer navigator line; the 12-step table is now labelled "new product only" and each step is skippable. Honest assessment: a modest gain; brainstorming was never gated.

### (j) Solo work with flaky connectivity
| Failure point | v0.5.0 | v0.6.0 |
|---|---|---|
| First commit offline | failed: pre-commit downloads hook repos (incl. the remote commit-msg hook) | commit-msg hook is local; hooks warmed at init (in the background, on a terminal) while online; `eos doctor` says "install hooks while online". **Still a risk** if init itself runs offline: then `SKIP=<hook>` or install later. |
| MCP | GitHub + Context7 servers on by default (remote calls time out) | `minimal` by default |
| Feedback loop | done = full check locally, then wait for CI over a slow link | `eos verify` locally in seconds; CI remains the final gate |
| Hotfix fetch | could hang | 15 s timeout, `--no-fetch` |

## 3. Slow-down risks, ranked (impact × frequency)
1. **The same ceremony for every change.** A typo got the full check, memory edits and a navigator call; a multi-module feature got a blocking plan. → Lanes.
2. **Per-request context in Cline:** ~4,450 tokens of MCP schemas on every request by default. → `minimal` MCP default (−3,350 per request).
3. **Per-task agent overhead:** `eos next --brief` after every verified task, two memory files, teaching text. → Cut; git history is the progress log; teaching off by default.
4. **No escape hatch** for spikes and hotfixes, which trains people to bypass everything. → `eos spike` / `eos hotfix` with guards still on.
5. **Full check as the definition of done**, duplicating pre-push and CI. → `eos verify` scales with the lane (related tests for standard).
6. **The greenfield 12-step BMAD flow presented as the default**, with MCP and model switching. → Golden path first; 12 steps for new products only; skippable.
7. **Offline first-commit failure.** → Local commit-msg hook, background hook warm-up, MCP minimal.
8. **Blocking on every suppression comment** (`# noqa`, `eslint-disable`), which trains reflexive override labels. → Soft warning in trivial/standard; blocking in risky and with `--strict`. Skips, removed asserts and lowered thresholds still block everywhere.
9. **Hook latency** (guard ~90 ms per call, commit ~1 s). → ~45 ms and ~0.4 s.
10. **Generated eos files tripping the user's own linters.** → `.eos/ruff.toml` excludes them.
11. **The navigator blocking on `.eos-new` files**, and generic steps you can't dismiss. → Note, not blocker; `eos next --skip`.
12. **Too many commands to remember** (34 in `eos --help`). → Help leads with five: `next`, `verify`, `lane`, `spike`/`hotfix`, `stats`. Everything else still works (no aliases removed).

## 4. Lanes and when each applies
See `docs/WORKFLOW.md` for the full table. Summary:
- **trivial**: only docs, copy, translations or images changed (agent rule files excluded). Hooks on changed files. No plan, no new tests.
- **standard**: the default. Hooks + related tests. Plan only for multi-session work, and it never blocks.
- **risky**: money/auth/crypto/PII words in paths, migrations, infra, CI, gate configs, or a large diff. Full check + strict test-integrity, a 5-line plan (blocking when money, auth or security behaviour changes), human line-by-line review of flagged files.
- **one-way-door**: a migration that drops, renames or retypes data; removed lines in an OpenAPI/AsyncAPI/proto/GraphQL contract; a deleted migration. Approval before merge, ADR, rollback or forward-fix.
- **spike** / **hotfix**: from the branch prefix (see above). The underlying risk class is still computed and shown.
Overrides: PR label `lane:<name>` or `EOS_LANE`, both logged and counted by `eos stats`.

## 5. What was cut, merged or made optional
- **Cut:** the per-task `eos next --brief` core line; the `navigator` skill pack (26 → 25 phase packs); seeded `memory/active-context.md` and `memory/progress.md` and their `eos check` warnings (the doctor still warns on old projects); the remote `conventional-pre-commit` hook; the init wizard's teaching question.
- **Made optional / default off:** teaching mode; the commit-msg stage (only with release-please); the GitHub and Context7 MCP servers (`minimal` default; `eos mcp use build` restores them); suppression blocking outside risky lanes.
- **Narrowed:** `eos check` on commit only when agent-context files change; stop check skips gitleaks (it runs at commit) and spike branches; pre-push type checks and tests run through `eos hook-run` so their time is logged.
- **Added (small):** `eos lane`, `eos verify`, `eos spike`, `eos hotfix`, `eos stats`, `eos next --skip`, a CI Lane step, `.eos/state/events.jsonl` (local, git-ignored).

## 6. Deliberately kept despite the friction
| Kept | Friction | Why it stays |
|---|---|---|
| no-commit-to-branch on `main`; PR + CI for every change | a branch and a PR even for a typo | one command each; the PR is the only record and the only place CI runs before `main` |
| gitleaks at every commit (incl. spikes) | ~a few hundred ms | a leaked key costs far more than the sum of every commit wait; spikes leak secrets too |
| guard: deny secret reads, force pushes; ask on destructive shell | rare prompts (0/58 benign in the corpus) | the measured false-prompt rate is zero, so the cost is negligible |
| test-integrity blocks new skips, removed asserts, lowered thresholds | occasional block | that is how an agent "gets to green" dishonestly |
| pre-push type check + tests when stack files changed | seconds to minutes at push | over a flaky link, failing locally is much faster than a CI round trip |
| stop check (fast hooks on files the agent changed) | ~0.4 s per "done" | stops "done" claims on code that doesn't lint |
| money/auth plan approval and human review; one-way-door approval | waits for you | irreversible or costly mistakes; this is the point of the system |
| the 6-question init questionnaire | ~1 minute, once | it picks profile, mode and packs, which is what keeps context small afterwards |
| cross-repo ceremony (linked PRs, contract checks) | several PRs | breaking another repo's consumer is a one-way door |

## 7. Self-metrics: `eos stats`
`eos stats [--days N]` (default 30 days) reads `.eos/state/events.jsonl` and git: guard calls and approval prompts per 100 calls (with the top reasons), guard p50/p90, stop checks and their block rate, git-hook p50/p90 per hook, `eos verify` runs by lane, spikes and hotfixes, lane overrides, skipped navigator steps, and lead time from branch to merge commit. Each line that crosses a threshold prints a tuning tip (for example: more than 5% of tool calls asking you, a stop check p90 over 60 s, or a git hook p90 over 2 minutes). Lead time needs merge commits; squash merges hide it, so use your forge's insights there. Nothing leaves the machine.

## 8. Deferred (not worth the complexity yet)
- Merging overlapping packs (ideation into discovery, ux-design into design-direction): they load on demand, so the saving is in skill-list tokens only (~10–20).
- An automatic coverage ratchet; CI parallelisation and caching beyond what the stack templates already do (needs live CI timings first); flaky-test quarantine (Google reported about 1.5% of test runs flaky; worth it once `eos stats` shows repeated reruns).
