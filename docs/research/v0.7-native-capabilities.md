# Native capabilities baseline (verified 10 October 2026)

Purpose: the v0.7 knowledge library must add what the tools and models **don't** already do, and must never fight or duplicate built-in behaviour. Every row below was checked on 10 October 2026 against the vendor's own documentation (links inline). Tools change monthly: re-verify before relying on a detail, and treat anything marked *reported* as a third-party or forum observation.

### Frontier models
Model names, context sizes and prices change monthly; eos does not pin them here (`eos models --check` verifies ids live). For reference, Cursor's own model list on the research date (https://cursor.com/llms.txt) included Claude Sonnet/Opus/Haiku 5.5, GPT-5.6 (Sol/Terra/Luna), Gemini 3.1 Pro and 3.8 Flash, Grok 4.5–4.7 and Composer 2.5. What matters for the library [Recommendation]: these models already know the textbook (caching, replicas, sagas, the system-design-primer material). What they lack is **your constraints, decision thresholds, the failure modes they tend to forget, and current versions**. The library should carry decisions and checks, not re-teach definitions.

## 2. What eos should NOT do
1. **No planner of its own.** Every tool has a plan mode. eos only decides *when* a plan is required (lanes) and where a multi-session plan is stored (`docs/plans/active/`).
2. **No in-session todo or progress tracking.** Focus Chain, Cursor/Claude todos and Codex `update_plan` do it. eos keeps only `memory/handoff.md` for cross-session and cross-tool handoffs and the stop-hook escalation.
3. **No checkpoints, undo or compaction.** All four tools have them.
4. **No session memory of its own.** Claude auto memory and Cline's Memory Bank exist; eos's shared, reviewed knowledge goes into git (ADRs, lessons, the library), never a second memory system.
5. **No review runner.** Native reviewers run reviews; eos packs are the rubric (code-review pack updated).
6. **No code or docs indexing, no docs MCP by default.** Instant Grep, Explore subagents and web fetch do it.
7. **Never the same skill in two folders a tool scans, never the same hook installed twice** (both found and fixed, below).
8. **No content duplicated between `CLAUDE.md` and `AGENTS.md`** (already: `CLAUDE.md` imports `@AGENTS.md`, which Claude Code never reads twice).
9. **No deep knowledge in always-on context.** Rules stay short; depth is loaded by skills and pointers only when the work needs it (Cursor: rule file mentions are not inlined; Cline: skill bundles load "as needed").
10. **No textbook re-teaching.** Library files carry decision criteria, numbers with sources, anti-patterns and checks.
11. **No must-hold rule as prose only.** If it must always hold, it is a hook, a pre-commit check or CI (vendor guidance agrees).
12. **No MCP server where a CLI does the job** (`gh`, `git`), since Cline pays MCP schemas on every request.

What eos still adds that no tool does: one source of truth rendered for four tools; deterministic gates that behave the same in every tool (guard, pre-commit, CI, test-integrity, budgets); risk lanes; lifecycle guidance; and a vetted, versioned knowledge library.

## 3. Duplications found in eos v0.6.0 and fixed in v0.7.0-dev
| Problem | Evidence | Fix | Measured effect (always-on, default `web-app`, all four tools) |
|---|---|---|---|
| Every intent pack was written to `.agents/skills`, `.cline/skills` **and** `.claude/skills`. Cursor scans `.agents` + `.claude`, Cline scans `.cline` + `.claude`: both listed each eos skill twice on every request. The v0.6 bench counted only one folder per tool, so it under-reported this. | docs above; `tests/bench/measure_context.py` now counts every folder each tool scans | `skill_dirs()` picks folders so each tool sees exactly one copy: with Claude Code selected, only `.claude/skills` (read by Cursor, Cline and Claude Code). Codex gets `.agents/skills` only when that wouldn't duplicate in Cursor; otherwise it uses `.eos/packs/INDEX.md` (AGENTS.md already says so). Same rule for the global skills `bootstrap` installs; stale copies are removed on `eos update` / `bootstrap`. | Cursor 2,347 → 1,884 tokens; Cline 2,277 → 1,860; Claude Code 1,907 (same); Codex 1,860 → 1,397 (no skill list; reads the index when needed) |
| In Cursor, eos's guard and stop check ran **twice** per event: once from `.cursor/hooks.json`, once from `.claude/settings.json` (third-party hooks, on by default). | https://cursor.com/docs/reference/third-party-hooks | The Claude copy steps aside when the payload carries Cursor's `cursor_version` / `workspace_roots` fields and eos's Cursor hooks are installed. Detection uses the payload, not environment variables, so `claude` started inside Cursor's terminal keeps its guard (tested). | One guard (~45 ms) per tool call and one stop check (~0.4 s) per "done" saved in Cursor |
| The code-review pack described AI review mechanics. | native `/review` commands above | Points to the native reviewers and keeps itself as the rubric. | none (on-demand pack) |

## 4. Gaps noted (not fixed in stage 1)
- **Codex hooks are not wired.** Codex now supports project hooks (`.codex/hooks.json`, trust required). eos's guard covers Cursor, Claude Code and Cline only; Codex relies on git hooks and CI. Candidate for a later stage (payload and tool names need their own tests).
- **Cline CLI hooks** live in `.cline/hooks/`; eos installs only the VS Code location (`.clinerules/hooks/PreToolUse`). Installing both may double-run in the extension; needs a test before changing.
- In Cursor, reads pass through both `beforeReadFile` and `preToolUse` (~45 ms each, same decision). Narrowing `preToolUse` needs Cursor's exact tool names for a matcher; deferred.
