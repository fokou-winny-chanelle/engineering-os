# Efficiency evaluation (v0.7.1): does engineering-os speed you up or slow you down?

Question: after stages 1–11 (v0.7.0: the deep-reference library, design studio, testing, ops, frontend, mobile, LLM and data gates), does eos still make a solo developer faster, or has it grown into friction? Method: the ten workflows from the [v0.6 velocity audit](v0.6-velocity-audit.md), re-run against the current system; hook, lane and verify latency measured on fixtures for v0.6.0, v0.7.0 and v0.7.1, interleaved; a real open-source project adopted end to end; tokens counted with the same scripts as every release. Where something slowed you down and the fix was small and safe, it was fixed in this release.

How to read the numbers:
- **Measured (M)**: wall-clock on the build box (Linux, Python 3.12), medians of 15 runs for hooks and 5 for `eos verify`, the three versions run in alternating rounds so machine noise hits all of them. Raw data: [`tests/bench/results-v0.7.1.json`](../../tests/bench/results-v0.7.1.json). Scripts: `tests/bench/bench_hooks.py`, `tests/bench/bench_lanes.py`, `tests/bench/measure_context.py`, `tests/bench/mcp_schema_tokens.py`. Your laptop will differ in absolute terms; the ratios are what matter.
- **Counted (C)**: steps, gates, commands and files read from what each version installs.
- **Estimated (E)**: human or agent time, and CI wall-clock. These are judgements, labelled as such. **No CI run was timed** for this evaluation.
- Tokens are characters ÷ 4 (real tokenisers vary by about 20%).

## Headline

1. **v0.7.0 had quietly made every eos command slower** (M): guard hook 42 → 54 ms per agent tool call, `eos lane`/`eos next`/`eos check` roughly 110 → 190–200 ms, stop check 0.42 → 0.50 s. Cause: `eos.py` grew from about 7k to 13.5k lines and was executed as a script, so Python recompiled it on every call (169 ms compile alone), plus the full 48-command parser and ~70 regular expressions were built even for a 40 ms hook. **v0.7.1 is faster than v0.6.0** on every measured path (table in section 1).
2. **Day to day, the extra v0.7 features cost you almost nothing unless you use them** (C): the 134 deep references load only when an agent opens one, the 33 scaffolds are opt-in, the extra verify gates are millisecond checks that only fire when relevant files exist, and the always-on context is unchanged since v0.6 (Cline 1,860 tokens per request).
3. **The one real friction found was in adopting and updating** (M on a real repo): every adoption PR and every `eos update` PR came out "risky" with **33 eos files** listed for line-by-line human review, because eos's own files are called things like `eos-security.md` and `ref/security/payments.md`. Fixed: eos files that are byte-identical to what eos wrote no longer count as sensitive or large; the gate configs and the manifest still do. Same PR now lists **5 files**, all genuine.
4. **Where eos genuinely costs time, it is on purpose** (C): risky money/auth changes (a 5-line plan, approved first if behaviour changes; full check; line-by-line review; stricter changed-line coverage in CI). That is the point of the system and was not loosened.
5. **Your biggest remaining cost is learning and setup, not runtime** (E): about half a day on day 1 and a few hours spread over week 1, versus runtime overhead of seconds per task. Section 6.

## 1. Measured: the inner loop

| Measurement (M, medians) | v0.6.0 | v0.7.0 | v0.7.1 |
|---|---|---|---|
| Guard hook per agent tool call, read / edit / shell | 42 / 42–44 / 48 ms | 54 / 54 / 60–72 ms | **40 / 40–42 / 46 ms** |
| `eos lane` | 113–118 ms | 186–202 ms | **59–65 ms** |
| `eos next` | 120 ms | 199 ms | **63 ms** |
| `eos check` (fixture) | 108–111 ms | 195 ms | **64–66 ms** |
| `git commit` (docs or `.py`, all hooks) | ~390–404 ms | ~390–404 ms | ~390–404 ms |
| Stop check when the agent says "done" | 411–422 ms | 494–500 ms | **343 ms** |
| `eos verify`, trivial lane (docs) | 479 ms | 598–616 ms | **413–423 ms** |
| `eos verify`, standard lane (one module + its related pytest file) | 638–659 ms | 717–731 ms | **599–624 ms** |
| `eos verify`, risky lane, eos's own overhead* | 537 ms | 631 ms | **482 ms** |

\* The risky lane runs the project's full check; on the fixture that step needs a network `uv sync`, so the row shows eos's own part only. On a real project the full check is your test suite's time, the same in every version.

Fixture: 61 Python modules with 61 pytest files, a `payments/` module and a small web app (`tests/bench/bench_lanes.py`). Guard false-prompt corpus unchanged (M): 0 of 58 benign commands prompted, 17 of 17 risky asked, 9 of 9 denied.

What a typical 40-tool-call agent task pays in guard time (C × M): v0.6.0 ~1.8 s, v0.7.0 ~2.3 s, v0.7.1 ~1.7 s.

**Fixes made (v0.7.1):**
- Projects get a 13-line `.eos/bin/eos.py` stub that *imports* `eos_impl.py`, so Python caches the compiled bytecode (script run 216 ms → 72 ms when imported, M).
- The guard hook takes a fast path that skips building the 48-command argument parser.
- Module-level regular expressions compile lazily, on first use (eos's own import 10.5 → 4.3 ms, M).
- The `eos` command on your PATH imports eos the same way.

## 2. Measured: a real project

Repository: [fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template) at commit 7257e60 (252 tracked files, FastAPI + React + Playwright, 15 CI workflows of its own).

| Step (M) | Time / result |
|---|---|
| `bootstrap` (machine setup, no network) | 187 ms |
| `eos adopt` (scan, merge without clobbering, ratchet, plan) | 428 ms, 247 files added |
| `eos check` | 75–83 ms warm |
| `eos lane` / `eos next` | 78 ms / 67 ms |
| CI-equivalent eos steps locally: check + lane + test-integrity | ~0.23 s together |
| gitleaks on the full history (the CI secrets job's work) | 0.70 s |
| Lane on the adoption branch, v0.7.0 | **risky**: 33+ "sensitive" eos files + "large change" |
| Lane on the adoption branch, v0.7.1 | **risky**: 5 files to review (`.eos/config.json`, `.eos/protected.txt`, suggested pre-commit config, `eos-core.yml`, the manifest); 229 eos files exempted as unchanged |
| Lanes after adoption | `config.py` standard, `routes/login.py` risky, `README.md` trivial: correct |

Risky-path coverage on this repo (M): 22 of 155 code files (14%) match a sensitive word or path. 20 are clearly auth, password or migration code. Two are borderline: a `password-input.tsx` UI component and a `reset_password.tsx` email template. Both still count as risky (the price is a 5-line plan and a careful review); add a `lanes.trivial` or narrower `risk_words` entry in `.eos/config.json` if they annoy you.

Adoption keeps the repo's existing CI and adds one workflow, `eos-core`, with three small parallel jobs (C).

## 3. Measured: tokens

MCP tool schemas (M, `tests/bench/mcp_schema_tokens.py`). Cline sends these on every request for every enabled server; Cursor, Claude Code and Codex load tools on demand.

The `design` profile in Cline now costs ~4,120 more per request than in v0.7.0 because it includes the browser. Over a 30-request session that is roughly 120k extra input tokens (E, assuming 30 requests). Use `minimal` when you are not checking pages visually.

## 4. The ten workflows, re-run (v0.6.0 → v0.7.1)

Notation as in the v0.6 audit: agent actions beyond the change itself / local gates / artifacts / blocking approvals. Tokens: Cline's always-on context plus the default MCP profile, ~3,070 per request, in every row unless noted.

| Workflow | What changed since v0.6.0 (C) | Gates and waits (C, M) | Approvals (C) | Verdict |
|---|---|---|---|---|
| (a) 10-minute Python bug fix | Nothing in the flow. `eos verify` may add a millisecond flaky-quarantine check if you use quarantine. Optional `debug` MCP profile to inspect the local DB (+1,220 Cline tokens only while on). | verify 0.60 s, commit 0.40 s, stop check 0.34 s, guard ~40 ms per call | none | Slightly faster than v0.6.0 |
| (b) Typo / copy change | Nothing | trivial lane; verify 0.41 s; commit 0.39 s; CI: path filters skip stack CI, only `eos-core` runs | none (PR still required) | Faster |
| (c) Medium feature, 1–2 days | New: PR CI gates **changed-line coverage at 80%** when the stack CI produces a coverage report (pytest-cov / vitest / flutter). A large diff (>20 files or >400 lines) is risky, as before. | per task verify ~0.6 s; one new CI gate that can fail a PR | none unless risky | One new way to be blocked in CI; it catches untested new code, which is what AI-written code most often is |
| (d) Risky money/auth change | New: 90% changed-line coverage on money/auth paths in CI; a note pointing at mutation testing (opt-in scaffold); the payments/auth/security references load when relevant (~2k tokens each, on demand). | verify = full check + integrity, eos overhead 0.48 s | 5-line plan approved first if behaviour changes; human line-by-line review | Slower on purpose; nothing loosened |
| (e) Spike | Nothing | guard + gitleaks only | none | Same |
| (f) Adopt a messy repo, ship a fix the same day | Adoption PR no longer lists dozens of eos files (fixed in 0.7.1). The adoption adds 125 reference files (1.2 MB) under `.eos/packs/ref`. | adopt 0.43 s on 252 files; check 75 ms | adoption PR: 5 files to review; CI's test-integrity asks for the `test-change-approved` label because `.eos/` changed (since v0.6) | Faster than v0.7.0; one label click per adoption or update PR, deliberate |
| (g) Night-time hotfix | Nothing | 15 s fetch timeout; verify by lane | money/auth files still flagged for a second person | Same |
| (h) Cross-repo change | Contract checks now also cover data contracts (`eos data check`) | per repo | one-way-door when a contract loses lines | Same, safer |
| (i) Brainstorming | Discovery/ideation references available on demand | none | none | Same; never gated |
| (j) Flaky connectivity | Two new MCP servers, both off by default and both local (Postgres on your machine, a headless browser on localhost). First run downloads them once (uv / npx). | first commit offline: still a risk if `eos init` itself ran offline | none | Same; download the MCP servers while online |

**Pending human sign-offs** (C): 8 vendored packs are unsigned. They block nothing in your daily flow; `eos vendor check` only warns. What you lose is their content: the design studio (`eos studio install`) refuses unsigned sources until you review them. That is unrealised payoff, not friction.

**Commands and concepts** (C): top-level commands went from 34 to 47. Several of the new ones are called by hooks or CI rather than by you (`diff-coverage`, `quarantine`, `mutation-plan`, `mutation-score`, `bundle-size`). `eos --help` starts with "the five you need day to day" (`next`, `verify`, `lane`, `spike`/`hotfix`, `stats`). New concepts you meet only when you opt in: scaffolds, deep references, vendor sign-off, MCP profiles.

## 5. CI wall-clock per lane (structure counted, time estimated)

No CI run was timed. What is known: eos adds one workflow (`eos-core`, three parallel jobs). Locally its work takes ~0.23 s (eos steps) plus ~0.7 s (gitleaks) on the real repo (M). On a hosted runner each job also pays runner start, checkout and, for gitleaks, a container pull. That overhead was not measured. Because the jobs run in parallel with your own CI, they should add little or nothing to a PR's total wall-clock whenever your test jobs take longer (E).

| Lane | eos-core | Stack CI (`ci-python` etc.) | New since v0.6 |
|---|---|---|---|
| trivial (docs) | 3 jobs | skipped by path filter | none |
| standard | 3 jobs | lint, format, types, tests (+coverage), audit | changed-line coverage step (needs a coverage report; skipped with a warning otherwise) |
| risky | 3 jobs; the lane summary lists files for review | same | stricter changed-line coverage on money/auth paths; mutation testing only if you added the scaffold |

## 6. Setup and learning cost vs payoff (estimates)

| | Estimated time (E) | What you get |
|---|---|---|
| Day 1 | ~3–4 h: bootstrap and secrets (~20 min), `eos start` on one real project and read the lanes doc (~30 min), a first small fix through `next` → `verify` → PR (~1 h), MCP setup if wanted: Context7 key ~5 min, Postgres read-only role ~10 min, Playwright browser install ~5 min | guard, gates and lanes working on day 1 |
| Week 1 | ~3–5 h spread out: review the adoption PR's 5 files; learn spike/hotfix; decide on scaffolds (coverage, mutation, design); optionally review vendor packs (each needs a careful read, which is why it is your job and not the agent's) | changed-line coverage in CI, design critique loop, deep references in use |
| Ongoing, per task | ~1–2 s of eos runtime (M) plus the plan and review on risky work | — |

Payoff (E): the measured runtime cost is seconds per task. The return is mostly avoided incidents, and those cannot be measured on a fixture: a secret not leaked, a money rule not shipped untested, an unreviewed migration not run. Even one avoided incident pays for the setup time. The speed gains are concrete: one command (`eos verify`) instead of remembering which checks apply, related tests instead of the full suite, and agent context that stays at ~1.9k tokens however big the library grows.

## 7. Remaining risks of slowing you down, and fixes

| # | Risk | Impact | Fix |
|---|---|---|---|
| 1 | Adoption / update PRs flagged as risky with dozens of eos files | high, recurring | **Fixed in 0.7.1** (pristine eos files exempt; gate configs and the manifest still reviewed) |
| 2 | Every eos command ~2× slower in v0.7.0 | small per call, on every call | **Fixed in 0.7.1** (bytecode-cached stub, guard fast path, lazy regexes) |
| 3 | Cline asks for approval on every MCP tool call, so a screenshot-and-axe design loop means many clicks | medium for design work in Cline | **New opt-in in 0.7.1**: `EOS_MCP_CLINE_AUTO_APPROVE_SAFE=1` auto-approves only read-only tools (navigate, screenshot, snapshot, resize; schema, EXPLAIN, health). Clicking, typing, `browser_evaluate`, `execute_sql` and `browser_run_code_unsafe` still ask. Default unchanged. |
| 4 | Cline token cost of the `design`/`debug-ui` profiles (~5.3k per request) | medium, Cline only | Stay on `minimal`; switch with `eos mcp use debug-ui` only for visual checks |
| 5 | Changed-line coverage can fail a PR | medium | Intended. Override per repo with the `DIFF_COVERAGE_MIN` variable, or in `testing.*` in `.eos/config.json`. |
| 6 | Every adoption/update PR needs the `test-change-approved` label (`.eos/` is a gate config) | small, deliberate | Kept: eos's code *is* the gate; changing it should be a human decision |
| 7 | 1.2 MB of references copied into each project; code search may surface them | small, not measured | Not changed. If search noise bothers you, exclude `.eos/packs/ref` in your editor's search settings. |
| 8 | 47 commands look like a lot | learning cost only | `--help` leads with the five you need; the rest are setup, opt-in or called by CI |
| 9 | Unsigned vendor packs: content unused | lost payoff | Review them when you have an hour (`eos vendor review`); the agent must not do it for you |
| 10 | Offline first commit if `eos init` itself ran offline; MCP servers download on first use | rare | Run init and each MCP server once while online |
| 11 | Two borderline "risky" UI files (`password-input.tsx`) | small | Tune `lanes` in `.eos/config.json` per repo |

## 8. How to use it day to day

1. Start every task with `eos next` (or just ask the agent). Finish with `eos verify`. Read the lane line: trivial and standard need nothing more from you.
2. When the lane says **risky**, slow down on purpose: read the 5-line plan, then review the listed files yourself. That is where eos earns its keep.
3. Throwaway idea: `eos spike <name>`. Production on fire: `eos hotfix <name>`. Don't use `--no-verify`.
4. MCP: stay on `minimal`. `eos mcp use debug` when chasing a slow query against your **local** database; `eos mcp use debug-ui` (or `design`) to let the agent screenshot your local app and run axe; switch back afterwards if you use Cline.
5. Once a week: `eos stats` to see what eos costs you; `eos update` when a new version lands (expect one PR with ~5 files to review and the `test-change-approved` label).
6. When you have an hour: review one vendor pack, or add the coverage scaffold to a project that lacks it.

## 9. What was not measured

CI wall-clock on hosted runners; time on your own laptop; Postman and Figma MCP schemas (they need accounts); search noise from `.eos/packs/ref`; actual learning time (section 6 is an estimate); index advice in Postgres MCP (needs the `hypopg` extension, which the box doesn't have).
