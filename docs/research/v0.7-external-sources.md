# External sources survey (verified 10 October 2026)

What exists publicly that the eos knowledge library should import, adapt or link, judged on quality, maintenance, licence, security (prompt-injection) risk and token cost. Every repository below was checked through the GitHub API on 10 October 2026 (stars, licence, last push, archived flag); licences were read from the licence file when the API said "none" or "NOASSERTION". Star counts are a popularity signal, not a quality score.

Legend. **Import** = vendor verbatim, pinned (section 3). **Adapt** = write our own text, cite and attribute (allowed by the licence). **Link** = cite only (licence or quality does not allow more). **Avoid** = not worth the risk or the tokens.

## 2. Recommendation for stage 1 (architecture)
No verbatim import is needed: the best architecture material is either link-only (microservices.io, Builders' Library, SRE books, NC-ND repos) or textbook knowledge models already have. The architecture library is therefore **original text** with decision criteria, numbers and anti-patterns, citing the sources above (Azure patterns, Builders' Library, PostgreSQL docs, microservices.io, Fowler). **Imported in stage 1: nothing** (`packs/vendor/` is empty; `eos vendor check` passes with 0 sources). Planned imports, each in its own stage: `anthropics/skills` `frontend-design` (design), `vercel-labs/agent-skills` React/web-design skills (frontend), OWASP cheat-sheet extracts kept share-alike (security). **Stage 2 update:** the OWASP extracts are now vendored and quarantined pending human sign-off; see `v0.7-security-sources.md`.

## 3. Import policy
1. **Order of preference: link > adapt > vendor.** Vendor only when the exact text is the value (a maintained skill), never to save writing.
2. **Licence gate.** Vendor only permissive (MIT, Apache-2.0, BSD, CC0, CC BY) or share-alike (CC BY-SA, kept isolated with its licence). Never NC, ND, "all rights reserved", source-available or no licence. The licence file is copied next to the files, and the SPDX id is recorded.
3. **Pin.** A full commit SHA (a tag is recorded too, never trusted alone). Updates are explicit (`eos vendor update`), never automatic.
4. **Review for injected instructions.** `eos vendor` scans every vendored file for: instructions to ignore or override other rules; requests to read secrets, env vars or tokens; `curl|sh`-style remote execution; unpinned remote script URLs; hidden HTML comments or zero-width/bidi characters; base64 blobs. Any hit blocks the import until a human reviews it and records the decision. Human review of the diff is still required (the `packs/vendor/` path is in the risky lane).
5. **Provenance file.** `packs/vendor/PROVENANCE.json`: source id, repository URL, commit, optional tag, paths, SPDX licence, licence file, SHA-256 per file, token estimate per file, fetch date, reviewer and review note, scan result.
6. **Token gate.** A vendored file that may load as a skill body must fit the library size budget (docs/LIBRARY.md); bigger files are references, loaded only by pointer.
7. **Command.** `eos vendor add|update|review|check|list` (docs/LIBRARY.md). `check` runs offline (hashes, licence present, scan clean, age), so it can run in CI.
