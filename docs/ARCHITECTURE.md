# How engineering-os works

## Layers (most stable at the top)
| Layer | Lives in | Loaded | Size budget |
|---|---|---|---|
| L0 Personal profile | `personal/PROFILE.user.md` (git-ignored) or the `personal/PROFILE.md` template → each tool's global instructions | always, every project | ≤400 tokens |
| L1 Core rules + product profile + stack checks | `AGENTS.md` eos blocks (from `core/AGENTS.core.md` and the init questionnaire); the pack index lives in `.eos/packs/INDEX.md` (read on demand) | always | ≤1,100 tokens (AGENTS.md total ≤1,600) |
| L2 Stack packs | `.eos/packs/stacks/*.md` → rules with globs, scoped to the stack's directory | when a matching file is in play | ≤1,200 each; path rule ≤800 |
| L3 Phase packs | `.eos/packs/phases/*.md` → glob rules (Standards + Automated checks only) and/or skills (whole pack) | when the files or the intent match | ≤1,200 each; path rule ≤800; all skill descriptions ≤500 |
| L3b Deep references | `.eos/packs/ref/*.md` and `.eos/packs/ref/<area>/<topic>.md` (installed only when a selected pack points to them; see `docs/LIBRARY.md`) | only when a pack's `## Deep references` points to them and the agent does that work | ≤ 3,000 per area ref (`eos library lint`); never always-on |
| L4 Project memory | `memory/`, `docs/adr/`, `docs/ai/lessons.md` | `memory/handoff.md` when resuming unfinished work (v0.6: git history is the progress log); ADRs on demand | handoff ≤30, lessons ≤40 lines |
| L5 Session | chat, plan, `memory/handoff.md` | this session only | handoff ≤30 lines |
| L6 Deterministic checks | pre-commit, CI, hooks, `eos check`, `eos test-integrity` | always enforced; costs no tokens | n/a |

The rule of thumb is to **push knowledge down the table**. Prose (L1–L3) is the most expensive layer and the least reliable. A check (L6) is free at runtime and can't be ignored. The lifecycle of a rule is: *lesson → pack rule → automated check → delete the prose.*

## Just-in-time loading
- **By path.** `files` and `both` packs become Cursor `.mdc` rules with `globs`, Cline `.clinerules/*.md` with `paths:`, and Claude Code `.claude/rules/*.md` with `paths:`. They attach only when the agent works on matching files. A path rule carries only the edit-time part of a phase pack (Standards + Automated checks) plus a one-line pointer to the full pack; entry, deliverables, exit checklist and handoff are read when a phase starts or ends. Path rules never carry a `description`, so nothing is listed twice. Stack-pack globs are prefixed with the stack's directory (`web/**/app/**`), so a FastAPI `api/app/` file doesn't pull in Next.js rules.
- **By intent.** `intent` and `both` packs become skills (`.agents/skills`, `.cline/skills`, `.claude/skills`). Only their one-line descriptions are always visible (about 490 tokens for all 19 in v0.5; a project gets only its profile's subset; capped at 500 by `eos check`); the body loads when the task matches.
- **By project profile (v0.4).** The profile chosen at `eos init` installs only the skill packs that fit the product (e.g. an API project gets 12 of the 16), and switching profile removes the others. Files-mode packs are always installed because they cost nothing until a matching file is edited. See `docs/PROFILES.md`.
- **Tools without scoped rules** (e.g. Codex, or any `AGENTS.md`-only agent) read `.eos/packs/INDEX.md` (one line per pack, ~650 tokens) when they need a pack, then only that pack. The index is not in `AGENTS.md`, so tools that auto-attach packs don't pay for it every turn.
- **Stack detection.** Marker files are scanned to depth 3, skipping `node_modules` and `.venv`:
  - `pyproject.toml`, `requirements.txt`, `uv.lock`, … → python; plus `fastapi`/`flask` found in them → the flavour pack;
  - `package.json`/`tsconfig.json` → typescript;
  - `next.config.*` → nextjs (which requires typescript);
  - `go.mod`, `Cargo.toml`, `composer.json`, `pubspec.yaml`, … → reported as "no pack yet, run `eos new-stack`".

Cline's default MCP profile is now `minimal` (~1,250 schema tokens per request instead of ~4,450). See CHANGELOG 0.6.0 and `docs/research/v0.6-velocity-audit.md`.
v0.5: session start is about 2.0–2.1k tokens on the same fixture (default `web-app` profile: Cursor 2,040, Cline 2,016, Claude Code 2,063, Codex 2,016; teaching off saves ~30). The increase over v0.4 is the next-step core line, the navigator skill description and, in multi-app repos, a short topology block (see CHANGELOG 0.5.0). Path rules while editing are unchanged. Before v0.5: session start was about 1.8–1.95k tokens depending on the project profile (v0.4: AGENTS.md ~1,100 with the product-profile block + personal profile ~280 + skill list ~300–410, plus CLAUDE.md notes in Claude Code); it was 1.7k in v0.3. ## Lifecycle modes and the navigator (v0.5)
- **Modes**: greenfield, brownfield, rewrite (alias refonte), maintain. `detect_mode` suggests one from offline facts (source and test file counts, git commits, tags and age, a migration plan on disk) and prints the evidence; the manifest keeps the confirmed value (`eos mode set`). Modes add skill packs through `by_mode` in `core/profiles.json`.
- **State machine**: `core/lifecycle.json` (copied to `.eos/lifecycle.json`, editable) lists, per mode, ordered phases with declarative exit criteria: `exists`, `glob_min`, `filled` (a template placeholder is gone), `checked` (all boxes ticked under a heading), `tables` (each named heading has a table with at least one row), `table_status` (every row of a table has a status), `state` (computed facts such as "all stories done", "P0/P1 plan items done") and `any`. The current phase is the first with an unmet criterion. No code runs and nothing is sent anywhere.
- **`eos next`** = blockers first (failing gates from the last `eos check` / `eos ratchet check`, an unfinished handoff, uncommitted work on a protected branch, or the eos setup not committed yet), then work in progress (stories in progress or review, active plans), then the first unmet exit criterion of the current phase, with its reason and the exact command or agent prompt. With teaching on, it adds the pack the agent will use and an `eos explain` topic. Brownfield steps come from the first unchecked item of `docs/plans/improvement-plan.md`.
- **Agent side** (v0.6): one core line, "asked 'what next?': run `eos next`". The v0.5 per-task line and the `navigator` skill were cut (a tool call and ~900 tokens per task for a suggestion that was usually ignored). `.eos-new` files are a note, not a blocker. `eos next --skip` records skipped steps in the manifest (`nav_skip`). Teaching mode is one optional line in the product block. `eos explain` reads `.eos/concepts.md`, which is never loaded into agent context.

## Existing code: adopt and the ratchet (v0.5)
- **`eos adopt`** = offline scan → `cmd_init` with the Writer in *adopt* mode → ratchet baseline → reports. Adopt mode never overwrites a file eos didn't create: eos's version goes to `.eos/suggested/<path>`. `AGENTS.md` gets marked blocks around the user's text; a user `CLAUDE.md` gets a 3-line `@AGENTS.md` import block; a `.clinerules` *file* blocks Cline rules (reported, not replaced); existing CI stays and only `eos-core.yml` is added. The manifest records `adopted: true`, so later `eos update` runs keep the same rule.
- **Scan** (no network, no builds): languages, frameworks from manifests, build/test commands (package.json scripts, Makefile, justfile, Taskfile, pytest/tox/nox), CI, lint/format configs, agent rule files with sizes, top folders, test ratio, coverage reports (Cobertura, lcov), lockfiles, declared and loosely pinned dependencies, update bots, git contributors and 12-month churn hot spots, large files, TODO count and tracked secret-like *file names* (never contents).
- **Ratchet** (`.eos/ratchet.json`, `.eos/baseline/*.json`): checks are commands from the project's own toolchain (ruff, mypy, eslint, tsc, import-linter, dependency-cruiser; or `eos ratchet add`). Output is parsed into fingerprints (file + normalised message; line numbers and digits dropped, so moving code isn't "new"). A check fails only when a fingerprint occurs more often than in the baseline; `update` / `--tighten` lowers it. A command that crashes without findings is *skipped*, never baselined as zero. In ratchet mode the AGENTS.md stack table says "format only the files you changed", pre-commit gets a pre-push `eos-ratchet` hook, and the strict hook set waits in `.eos/suggested/pre-commit-strict.yaml` until `eos gates strict`.

## Topologies and workspaces (v0.5)
- `detect_topology` returns single, monorepo, modular-monolith or microservices with evidence (see docs/PROFILES.md for the rules). Monorepos wire **every** directory per stack: per-dir pre-commit hooks scoped by `files:` and one CI workflow per (stack, dir) with path filters.
- Modular monolith: a topology block in AGENTS.md, a module catalog, `eos scaffold boundaries` (import-linter independence contract or dependency-cruiser rules that allow only a module's public API), `eos new module`.
- Microservices: a service catalog seeded with each service's contract, `eos new service` (README, OpenAPI, Backstage `catalog-info.yaml`, a service AGENTS.md) and the topology + api-design skills.
- **Multi-repo workspace**: the parent folder gets `eos-workspace.json`, an `AGENTS.md` (how to work across repos, repo table, contracts), `CLAUDE.md`, a `.code-workspace` file with the workspace folder first, and `.clinerules/` with one path-scoped pointer per repo plus each repo's path rules re-prefixed (Cline loads rules only from the first folder). Its own file hashes live in `.eos/workspace-files.json`, so it is never mistaken for a project. Each eos repo gets a short workspace block; repos adopted later join automatically. `eos workspace change` writes a cross-repo plan with merge order (contracts first) and one branch name.

## Anti-loop safeguards (defence in depth)
1. **Rules** (L1): stop after 3 fix attempts on the same failure; stop when the diff grows past 2× the planned files or reaches a protected path; or a long session gets confused. Then write `memory/handoff.md` and ask the human.
2. **Loop guard hook:** read-only commands (`rg`, `git status`, `git log`, `cat`…) never prompt and never count. Otherwise the *same command on the same code state* (a hash of `git status` plus `git diff`) more than 3 times → "ask" (Cursor, Claude) or cancel (Cline). Editing code between runs resets the count, so a normal test-fix-test cycle isn't blocked.
3. **Stop hook** (Cursor `stop`, Claude Code `Stop`): when the agent says "done", the pre-commit hooks run on the files changed *in this session* (files you left dirty before it started are ignored; gitleaks waits for commit time). Only the last 40 lines / 3,000 characters go back to the agent; the full log is in `.eos/state/last-check.log`. A timeout (e.g. first-run hook installs on a slow link) lets the agent stop instead of making it retry.
   - If they fail, the hook sends the failure back (attempts 1 and 2).
   - On attempt 3, it tells the agent to write a handoff and ask the human.
   - After that it lets the agent stop. Cursor's `loop_limit: 3` caps it as well.
4. **Hard blocks:** `--no-verify` and `SKIP=` (hook bypass), force-push, `curl | sh`, recursive deletes of `/`, `~` or `.`, printing the environment, reading secret files, and editing protected paths.

## Self-checking and self-optimisation
- **Verification is deterministic.** "Done" means the stack's `full_check` command is green, and CI runs it again. The model's opinion of its own work doesn't count.
- **Anti-reward-hacking.** `eos test-integrity` flags:
  - new skip, only or xfail markers;
  - new suppression comments;
  - net removal of assertions;
  - deleted test files;
  - lowered coverage or mutation thresholds;
  - edits to quality-gate config.
  CI then requires a human to add the `test-change-approved` label.
- **Independent review.** The code-review pack plus BMAD `bmad-code-review`/`bmad-review` run in a **fresh context** or with a different model. A human approves anything touching money, auth, crypto, migrations or infra.
- **Retros.** The `eos-retro` skill turns repeated mistakes into the cheapest durable fix, in this order: check > pack line > lesson. It also prunes context files back under budget. Changes that are general go upstream to this repo, and `eos update` ships them to every project.

## Ownership and updates
- `.eos/manifest.json` stores the eos version, the chosen tools, stacks and phases, and a hash for every managed file.
- `eos update` overwrites a managed file only if its hash still matches, i.e. you haven't touched it. Otherwise it writes `<file>.eos-new`.
- The eos blocks in `AGENTS.md` are always refreshed. Your "Project specifics" section (and BMAD's context block) is never touched.
- Adapters are **generated**. Edit `.eos/packs/*` and run `sync`; `eos check` in pre-commit and CI fails on drift.

## Velocity: lanes, verify, escape hatches, self-metrics (v0.6)
- **`classify_change`** reads `git diff -U0 <merge-base>` plus untracked files: paths (risk words matched as whole words after splitting on `/ _ . -` and camelCase, so `tokens.css` and `authors.py` stay standard), migration/infra/CI/gate-config paths, size (> 20 files or > 400 lines), and content (dropped or renamed columns in migrations; removed lines in OpenAPI/proto/GraphQL contracts). Branch prefixes `spike/` and `hotfix/` set the lane; the risk class is still reported. Labels `lane:<x>` or `EOS_LANE` override, logged.
- **`eos verify`** builds a plan per lane: `pre-commit run --files <changed>` first (formatters may fix files; re-run once), then in parallel per app dir: related tests (pytest: changed test files plus `test_<module>.py` for changed modules; `vitest related --run`; `jest --findRelatedTests`) or, for risky lanes, the stack's `full_check` once per dir; then test-integrity. Testing gates (v0.7 stage 5, all in-process): standard and heavier lanes check `tests/quarantine.json` for expired or incomplete entries; risky, one-way-door and `--full` also run `eos diff-coverage` when a coverage report newer than the changed files exists (otherwise a note), and remind that the CI mutation job covers changed risky source. Operations gates (stage 6, in-process): standard and heavier lanes run `eos ops check` (SLO file, alert rules need severity and an existing runbook, flags registry and expiry, stale generated burn-rate rules) only when those files exist; risky, one-way-door and `--full` run hadolint on changed Dockerfiles, and `--full` runs checkov on changed IaC folders, each only when installed (otherwise a note: CI runs them). Frontend gates (stage 7, in-process): standard and heavier lanes run `eos i18n check` only when translation catalogs exist; risky, one-way-door and `--full` run the gzip bundle ratchet (`eos bundle-size`) only when a build output newer than the changed web files exists (otherwise a note). Design gates (stage 8, in-process): standard and heavier lanes run `eos design check` only when UI or token files changed: DTCG schema and WCAG 2 contrast over all token and theme files, the generic-look lint over the changed files (the whole repo on risky, one-way-door and `--full`); lint findings are notes unless configured as errors. Mobile gates (stage 9, in-process): standard and heavier lanes run `eos mobile check` (Android manifest, network security config, iOS ATS, Expo config, public env names) only when mobile config files changed; risky, one-way-door and `--full` also run the app-size ratchet (`eos mobile size`) only when a built .aab/.apk/.ipa newer than the changed files exists (otherwise a note). Emulator E2E (Maestro) stays in CI. LLM gates (stage 10, in-process): prompt files are never trivial; standard and heavier lanes run `eos llm check` on changed prompt files; risky, one-way-door and `--full` check all prompt files and run `eos llm gate` only when an eval results file newer than the change exists (otherwise a note). Real model evals stay in CI (same-repo PRs, nightly, manual). Data and ML gates (stage 11, in-process): standard and heavier lanes run `eos data check` on changed ODCS contracts (`*.odcs.*`, `contracts/`) and tracked notebooks, including breaking changes against the lane base (DAT006), and print a `dbt build --select state:modified+` note when dbt files change; risky, one-way-door and `--full` check every contract and notebook. `*.odcs.*` files count as public contracts in lane classification. dbt builds stay in CI (the analytics workflow). The opt-in design studio (`eos studio`) is never part of verify, hooks or any lane. Trivial and spike lanes get nothing new; mutation, load, long property runs, promtool, IaC plans, Lighthouse CI and Playwright stay in CI. No related tests found → it says so; the full suite still runs at pre-push and in CI.
- **Hooks**: agent hooks start through `.eos/bin/hook.py`, which imports `eos.py` so Python caches its bytecode (guard median 88 → 42 ms on the bench). The loop guard fingerprints `git status` plus the size and mtime of changed files instead of hashing the whole `git diff`. Commit hooks: `eos check` only when agent-context files change; no commit-msg stage unless release-please is set up (then a local `eos commit-msg` hook). Pre-push hooks run through `eos hook-run`, which logs their duration.
- **Events**: `.eos/state/events.jsonl` (git-ignored, rotated at ~1 MB): one line per guard call (mode, decision, ms; reason only for ask/deny), stop check, verify, git hook, spike/hotfix, override and navigator skip. `eos stats` summarises it with percentiles and tuning tips, plus lead time from merge commits.
